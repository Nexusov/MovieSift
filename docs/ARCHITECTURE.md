# Architecture

MovieSift is one desktop process with short-lived MKVToolNix or FFmpeg/ffprobe workers. Its four application layers form a modular monolith. A small `MovieSift.Updater` entry point runs the portable update helper after the desktop exits:

```text
Desktop -> Application -> Core
Bootstrap -> Infrastructure -> Application / Core
```

Core contains immutable source/track descriptions, approved retention plans, and pure selection validation. Application coordinates inspection, single jobs and sequential batch state through narrow media/filesystem/persistence ports. Infrastructure owns format-specific JSON/XML, argument arrays, worker processes, source revisions, bounded discovery, safe output publication, and portable JSON. Desktop owns typed compiled XAML bindings, observable ViewModels, native file dialogs, localization, and the composition root. Only `Bootstrap` selects Infrastructure implementations; ViewModels receive use cases/ports.

## Inspection and planning

Inspection records an actual detected container, source revision, pinned backend/version, and file-local track IDs separately from Matroska UIDs. Each batch item retains its immutable inspection. Selecting another details row cannot redirect a late result or change the aggregate scope.

The pinned JSON protocol is supplemented by a narrow read-only EBML Segment/Info traversal because it omits SegmentFamily. The reader checks linkage only at defined Info-child boundaries, seeks past finite payloads, bounds header count/lengths, and rejects ambiguous layouts. An unknown-sized Segment is bounded by EOF; unknown-sized clusters and repeated/nested document structures are unsupported. A shared regular-file opener checks the opened handle, including Linux nonblocking/no-follow open and `fstat`, before creating a stream. No third media executable is introduced.

Keep starts enabled for every audio/subtitle track. Video is always retained. Planning snapshots the inspected tracks and selections into an immutable plan; it rejects video removal and requires explicit confirmation when the last existing audio track is removed. Empty subtitle selection is normal. No-change plans produce a result without launching remuxing. Source/selection/destination changes invalidate the preview; UI-language changes only update presentation.

## MP4 adapter boundary

`ContainerMediaBackend` is explicitly composed with the MKV and MP4 adapters. Inspection routes a candidate suffix to an adapter that must establish its actual container. Remux/verification route exclusively by the approved inspection's `MediaContainer` and validate its pinned backend identity; neither file renaming nor a tool failure selects a fallback. `MediaTrack.Id` remains a backend-local input index, output indexes are separately probed, and `Uid` is nullable for MP4 rather than manufactured from an index. Immutable container properties hold adapter-owned bounded metadata facts without adding JSON dependencies to Core.

`Mp4BoxReader` reads schema-positioned capability fields from an established regular read-only handle, seeking over media/sample tables. It establishes actual brand, nonfragmented layout, self-contained references, ordinary sample descriptions/metadata and simple rate-one edits; unknown/unsupported representations fail before planning. `Mp4Probe` maps bounded structured ffprobe output and effective supported flags. The preservation matrix defines exactly which codecs, metadata, chapters, artwork and edit semantics are admitted; this is not a general ISO box parser.

`FfmpegArguments` maps each retained source index explicitly, stream-copies every mapped stream, copies admitted metadata/chapters and sets dispositions. External references/protocols and stdin are disabled. No automatic selection, encoder fallback, subtitle conversion or timestamp normalization is used. JPEG/PNG cover streams are always retained. A narrowly scoped candidate-only fixup corrects the pinned muxer's first-default promotion and loss of the in-preview bit: after FFmpeg exits and the candidate mapping is checked, it opens an identity-checked single-link regular candidate and restores only the approved enabled/in-movie/in-preview `tkhd` flags (mask 7). Unknown modes are rejected and final verification compares all admitted bits. Sources never receive a write handle. Failure leaves publication prohibited and cleanup with the existing owner.

MP4 verification re-probes the candidate, compares the approved mapping, codec initialization, complete admitted tags/dispositions/chapters, and streams packet records into constant-memory per-stream SHA256 fingerprints. Rational PTS/DTS/duration, payload sizes/order/count/hash and AAC skip/padding are checked without whole-movie JSON or extracted scratch payloads. Attached artwork has encoded-byte identity rather than an invented presentation timeline. The process result distinguishes retained-output truncation from truncated warning diagnostics and oversized machine records, so a long progress stream cannot conceal missing verification evidence. No tiny whole-remux/packet-scan timeout is imposed; cancellation uses the existing owned runner.

Ownership schema 3 also binds the output mode and, for replacement, the expected source and verified candidate revisions. Legacy versions 1/2 are accepted only as Copy. The record binds an explicit container to its fixed `candidate.mkv` or `candidate.mp4` layout and matching destination. Original version-1 records remain valid only as the exact legacy MKV layout; unknown or inconsistent versions/containers never authorize cleanup, publication or termination. Both formats share `JobCoordinator`, sequential `BatchCoordinator`, source/collision checks, warning ownership, mode-specific publication and cleanup. Queue and preset schemas acquire no stream indexes or execution authority.

## Runtime tool distribution

The candidate builds only `ffmpeg` and `ffprobe` from the same pinned FFmpeg source, with explicit static zlib and a disabled-autodetect local-file/pipe configuration. `FfmpegToolPaths` verifies its distinct `9.0.2-MovieSift-source-2a571b606854` identity. Complete source archives, the local recipe, actual configuration/compiler observations and hashed worker/material receipts accompany each build. Build-only GCC/MinGW-w64, Make, NASM and MSYS2 are not application runtime dependencies; no ffplay or optional external codec/hardware library is selected. A verified local cache may reuse an identified build; native platform CI constructs and executes its own workers. No bit-identical cross-toolchain result is claimed.

Linux MKVToolNix 102.0 executable bytes and the exact included/omitted AppImage payload policy remain unchanged. Windows builds the same version's CLI pair from pinned source and UCRT64 packages, without the GUI. QtCore remains required. The actual recursive PE-import closure, DLL-to-binary-package hashes, binary BUILDINFO-to-source PKGBUILD matches, complete source/patch archives and original notices accompany a hashed build receipt. A separate validation boundary checks every worker/material and actual import before acquisition; there is no official-binary fallback. Host-only build tools never become application prerequisites. Existing dependency, application, package, relocation and clean-container checks remain mandatory. The [distribution closure](verification/release-distribution-closure.md) keeps source delivery and owner decisions separate from build provenance.

Capability inspection admits at most one **distinct** referenced QuickTime chapter-track ID. Several media tracks may reference that same track. This preflight restriction closes the aggregate-chapter reporting gap before candidate reservation, without adding a general chapter parser or weakening the existing Nero/QuickTime consistency checks.

## Job ownership and publication

The Application job coordinator owns one approved plan, candidate, tool outcome, verification evidence, review decision, publication fact, and cleanup result. A gate prevents conflicting jobs. UI state disables conflicting edits while the job/review owns its plan.

Before handoff, reservation owns its partial directory, marker and journal. Atomic directory creation and retained directory/file identities prevent adoption of pre-existing or replaced paths. The first journal is create-without-overwrite. On failure/cancellation, rollback deletes only still-owned resources; changed/foreign paths remain intact. Rollback/temporary-write cleanup issues accompany the primary failure through `OperationFailureException.CleanupIssues` and `JobResult`; they are not lost when no `OwnedOutput` could be returned. A durable journal retained after incomplete rollback remains subject to normal strict interruption validation. Bounded JSON relinquishes its unique temporary name after commit and does not delete a later occupant or mask a primary error.

The lifecycle is validate, reserve an adjacent private output directory, persist ownership, remux into its candidate, wait/drain, verify, recheck the source, then publish or await warning review. Backend-normalized success only permits verification. MKVToolNix exit 1 requires explicit approval/discard after all required verification succeeds. FFmpeg nonzero exits and unrecognized/truncated successful warnings fail; only the exact documented pinned demux warnings may proceed, with diagnostics retained. Raw exit status remains independent of the normalized outcome. Warning approval revalidates the existing candidate and source; it never remuxes again. A close request during warning review offers remain-in-review or discard-and-close. Repeated close/discard requests are gated; the window awaits the one cleanup operation and remains open on cleanup failure.

A genuine NoChange plan still validates the admitted container, exact retained selection and current source revision, but creates no output and skips output-only path/root/extension/collision/access/capacity checks. Its unused destination is excluded from output-output collision sets. Every source, including unchanged and excluded rows, remains protected against another item's output. Copy cannot target any source; ReplaceSource may target only its own inspected source. A later selection edit needs a valid destination and a fresh Review.

The initial destination validation for changed plans requests an advisory additional allocation of the source length. Publication rechecks path safety, aliases and collisions with zero additional media allocation: the adjacent verified candidate already occupies its space, and rename does not require a second source-sized payload. Capacity advice is not a reservation; actual filesystem/tool allocation failures remain failures.

Publication checks pending cancellation before a short non-cancellable boundary. For Copy, the filesystem move enforces no overwrite at the operation itself; an earlier existence check is only validation. ReplaceSource uses the verified replacement and backup boundary described below. Source identity/size/modification are rechecked before work and publication; those checks do not cryptographically prevent a concurrent edit. A successful final output is never removed by temporary cleanup. Report the actual published path even if a later cleanup fails or cancellation arrives.

Each expected failure carries a stable error code and structured diagnostic details. Tool exit, verification, publication/path, cancellation, and secondary cleanup issues remain distinguishable. A cleanup error cannot replace a primary failure. The UI translates its own messages, preserving original filenames/media metadata and raw tool diagnostics.

## Output choice and source replacement

Copy remains the default. With no separate output folder, each input produces an adjacent `.trimmed` file; an explicit output folder and relative recursive paths remain available. `OutputMode` is immutable plan data rather than an inference from matching path strings. Changing the mode invalidates Review, and New queue resets it to Copy. Saved queue records retain the mode as intent only: Restore requires new inspection, selection and Review.

ReplaceSource targets only the plan's own exact source path. Sources remain read-only during remux and verification. After fresh source and candidate checks, the same job owner journals the commit and calls same-filesystem `File.Replace` with a unique backup in its private directory. The inspected original and verified candidate must be recognizable at the backup and final paths before publication is confirmed. A durable published record permits backup cleanup; failure or uncertain identity preserves the backup and journal. A published result is still reported if only later cleanup fails. NoChange does not reserve storage or replace a file.

Read-only files and multiply linked sources are not replaceable. Linux replacement preserves ordinary permission bits and requires matching owner/group; special privilege bits or extended POSIX access ACLs are rejected instead of silently changing access. Other filesystem metadata is not a blanket preservation guarantee. Platform replacement and revision checks do not provide a filesystem-wide transaction or exclude arbitrary external writers; interrupted/uncertain commits require manual review rather than blind rollback.

## Phase 2A batch boundary

`FileBatchInputDiscovery` implements one filesystem port for explicit files or one selected folder, with default-off recursive traversal. It applies the existing local regular-file/reparse policy, canonical path and file-identity deduplication, deterministic ordinal order and cancellation. One scan shares the 10,000-entry budget across every visited directory, including directories/non-MKVs; excluded descendants are not visited. The 100-entry addition/session limit includes visible failures. A root-at-depth-zero traversal permits 32 nested directories to bound stack/path growth. Every non-excluded directory is revalidated with the complete local-directory policy immediately before enumeration, including mounted network filesystems that have no reparse flag. Redirected/network directories, traversal failures and limits reject the entire recursive addition before acceptance. The MKV/MP4 suffix remains only a filter; `InspectionService` probes each accepted candidate. Cancellation during later inspection retains accepted rows.

`BatchSession` publishes immutable snapshots keyed by generated item IDs and full source paths. Every item owns its inspection/revision, current retained IDs, approval, inclusion and complete job result. Folder-derived items also retain immutable `FolderSourceOrigin` (selected root and relative file path). An already accepted canonical path/file identity wins later duplicates without replacing provenance or editor state; roots are never reconstructed from a queue-wide prefix. Edits invalidate the aggregate review and only the affected file's plan. `BatchReviewValidator` rechecks the independent plans created by `ReviewSelectionsAsync` against current source revisions; only changed plans require destination validation and participate in output-output collision checks. Copy outputs cannot match any source, including unchanged/excluded entries. ReplaceSource may target only its own inspected source; other-source and duplicate-output collisions still fail. There is no obsolete per-file `ApprovePlan`/alternate `ReviewAsync` route. A frozen review is consumed once. The single-job coordinator repeats its existing checks at work/publication time.

`BatchCoordinator` serializes probes and dispatches each approved plan to the existing `JobCoordinator`; it does not implement another remux/verification/cleanup lifecycle. One `BatchSession` and one shared job owner serve one or many inputs; there is no hidden single-file queue or execution state machine. Warnings, failures, cancellation and cleanup/termination uncertainty pause dispatch. Warning actions target the frozen item/job owner, even after changing the visible details row. They leave the queue paused. Explicit re-review/start is required for remaining work; a safety block cannot be erased by excluding a row. No-change plans reach the existing no-remux result.

`BatchViewModel` owns one awaitable UI operation and cancellation source, with stable lightweight `BatchItemViewModel` editors. Switching rows or language does not reconstruct another file's selections/plans. Progress is checked against operation generation, item and plan identities. Native dialogs and presentation stay in Desktop. Cancel/status controls remain outside the scrolling batch review. The shell retains language settings, interrupted-ownership discovery/cleanup, recovery choices and coordinated shutdown. It awaits shutdown/discard once and preserves cleanup failures; media work belongs to the unified batch coordinator. Unexpected escaped lifecycle exceptions conservatively block further dispatch rather than assuming worker ownership was released.

The live queue remains in memory; a separate bounded checkpoint contains unfinished listing intent only. Ownership journals describe individual temporary outputs and never grant a restored list permission to retry, clean or publish. Rules require explicit preview/application; no automatic application to later inputs, parallel remuxing, automatic retry or byte-offset resume is implemented.

`BatchCoordinator.StartNewBatch` acquires the existing operation gate and atomically replaces a safe session with an empty snapshot at the next review revision. It rejects busy or unresolved warning/cleanup/ownership state without changing the old snapshot and performs no I/O. Desktop requires confirmation for a nonempty list and binds consent to that revision; declining preserves presentation. Successful reset clears editors, review diagnostics and progress while retaining language and the output folder. Old editor/progress callbacks are rejected by the existing item, plan and operation identities. The same source may be added again, but receives a new inspection and explicit approvals; existing files and collision checks remain intact.

## Unified workspace and aggregate selection

Core `TrackGroupingPolicy` builds an immutable metadata key from kind, exact canonical language, title trimmed only at its edges, codec, audio channels, forced status and semantic dispositions. It reuses the language rules' explicit alias/exact-tag parser. Default/enabled flags remain original member details, not key fields. Unknown/conflicting/unsupported language yields a visible ambiguity and a singleton occurrence rather than an invented shared identity. No fingerprinting, filesystem access or probe is involved.

`BatchSession.CreateTrackProjection` projects every included inspection and authoritative Keep set. Each member binds item ID, the actual inspection/source revision and local track object/ID. Every duplicate occurrence remains present; file coverage counts distinct items, independently of occurrence count. Completed/no-change members remain historical and locked. The displayed tri-state derives editable members where present, with historical member choices separately visible. Highlighting a file changes details only.

`SetTrackSelection` validates the projection revision and every requested member before changing any item. Group edits affect exactly represented editable members; member edits use the same path. The subtitle-section shortcut sends one atomic request for all currently included editable kept subtitle occurrences, including duplicates and uncertain-language singletons. It performs no language inference, approval or media work; no applicable change leaves existing authority intact. Section collections retain the same group/member objects so ordinary edits do not replace focused controls. Inspection/list changes reject stale requests. Only changed files lose approvals; no-op edits preserve the exact snapshot/review. New inspections start with all tracks kept; old manual group choices never become future-file rules.

`BatchCoordinator.ReviewSelectionsAsync` is the sole ordinary UI approval action. Under the existing gate/session lock it captures current selection/destination inputs, creates independent `PlanBuilder` plans and requires file-specific zero-audio consent bound to the current revision. Equivalent unconsumed approvals retain their identities. The existing `BatchReviewValidator` checks all included unfinished items, sources and collisions before Run; unresolved included rows block it. Asynchronous completion is revision/phase guarded. Review never probes again, creates directories or dispatches a worker. The existing coordinator still rechecks each approved job before work/publication.

The Desktop aggregate component owns presentation and commands, not another set of Keep choices. Refreshing projections, switching details and EN/RU preserve selections; rules/preset Apply edits those same selections. Advanced rules and per-file exceptions remain subordinate to the common workspace. Historical native results retain their original binary/interface identity; no new native acceptance is inferred from controlled/headless tests.

The responsive `BatchView` places a compact file list beside aggregate tracks, rearranging the same controls into a collapsible file shelf at narrow widths. Filename/context/full-path presentation does not redefine file identity. Local-file drop calls the same awaitable `BatchViewModel.AddDroppedFilesAsync` discovery/inspection operation; folders retain the explicit Add folder flow. Recursive additions guide the user through output-root selection before scanning, without changing the Infrastructure traversal policy. Pending inspection, pause/cancel and maintenance actions are contextual, while warning, recovery and cleanup decisions remain persistent.

`ReviewCommand` opens a distinct structured review surface. Stable `BatchReviewRowViewModel` rows reference the actual immutable per-file plans or current item validation failures and delegate zero-audio consent to the existing editor. Counts distinguish changed files from NoChange; all-NoChange completion still goes through the existing no-remux job result. Review and Run remain separate physical controls, and opening review focuses inert heading text rather than Run. Run closes only the review surface before the owned operation, leaving later warning/cleanup decisions visible. Review opens before asynchronous validation and exposes the existing cancellation command while pending. Cancelled/invalid checks show explicit state, not successful zero counts. Only a valid current review exposes Run; recheck occupies a different position and appears only when needed. NoChange rows suppress copy/destination promises but retain optional source-track information. Presentation surfaces and animations grant no execution authority.

## Appearance and motion

The cosmetic overlay is a view-level keyboard scope: opening focuses its controls, covered workspace controls cannot receive focus/input, Tab/Shift+Tab cycle inside, and Escape closes only appearance and restores valid workflow focus. The media owner continues independently. Mandatory warning/cleanup decisions remain outside the overlay and closing it exposes them immediately. Rule/preset helper text uses the semantic muted brush at full opacity; actual composed pairs must meet the palette threshold. The narrow file shelf budgets the actual remaining height, clips/scrolls within its area and retains usable file and track viewports at the declared minimum. Headless geometry/input/rendering does not establish OS layout/scaling acceptance.

The Soft-inspired visual system uses shared semantic resources for warm light/dark surfaces, text, accent states, focus, errors and warnings. `AppearancePalettePolicy` derives hover/pressed/selection/on-accent colors and checks linearized-sRGB contrast against the actual admitted surfaces (4.5:1 text and 3:1 essential indicators). Invalid edits retain the last usable palette. Avalonia colors/brushes, the version-aligned official ColorPicker, live resource application and finite render-only motion stay in Desktop. Appearance edits never recreate workspace ViewModels or invalidate media selections, reviews or ownership decisions.

Application defines immutable cosmetic values and the narrow `IAppearanceStore` port, independently of the language-only `ISettingsStore`. Infrastructure implements `data/appearance.json`, schema version 1, maximum 65,536 UTF-8 bytes and depth 8. Strict complete-record validation and existing regular-file/reparse checks precede safe I/O. Saves use a fail-fast interprocess lock, flush an operation-owned sibling temporary file and replace within the same directory; cleanup cannot erase the previous record or an unrelated file. Missing means built-ins; malformed/incompatible records remain visible and unchanged unless explicitly reset. Cosmetic save failure is session-only appearance evidence, not a media safety block.

Desktop coalesces appearance writes and rejects delayed startup values after a newer edit. Save results are relevant to the current accepted configuration rather than temporary invalid editor revisions. Selected surfaces validate both primary and secondary text; an essential selected outline remains visible independently of decorative borders. Separate light/dark overrides preserve inactive values. Reduced motion cancels/disables new cosmetic effects without delaying cancellation, cleanup or publication. System reads the Windows client-area animation preference when available; unsupported/unavailable system detection defaults to reduced motion. Rendered headless themes and keyboard tests retain that scope and do not establish native desktop/scaling acceptance.

## Phase 2D1 recursive discovery and output preparation

The input checkbox captures recursive traversal for each Add Folder request and stays outside rule presets. Copy into a separate directory requires an explicit existing local output root; a root equal to or above the source root is rejected, and a descendant output subtree is excluded. Adjacent Copy and ReplaceSource instead set `UseSourceDirectories`, so they require no separate output root. All modes retain the same local-path policy, traversal limits and transactional rejection of incomplete scans. Composition supplies the actual portable data path, including inspection scratch/logs, and the existing output store supplies validated journal/marker-backed private candidate directories to exclude. An unfamiliar `.moviesift-*` name alone is not ownership evidence. Discovery reads only and never creates output directories.

For Copy, Core `OutputPathPolicy` derives the established `.trimmed.mkv` or `.trimmed.mp4` name from a validated native relative path and checks component-aware containment with `Path.GetRelativePath`; sibling prefixes, rooted relatives and parent traversal cannot authorize writes. Native filename semantics are retained, including literal Linux backslashes/colons. Desktop uses this pure policy for folder rows and preserves explicit-file flat naming. Shared-root changes re-derive eligible unfinished destinations from their original provenance, invalidate affected approvals, and leave completed/no-change results intact. Explicit per-file Copy destinations remain available. ReplaceSource always uses the item's original source path.

An immutable Copy plan optionally captures `OutputDirectoryRoot`. Only folder-derived approvals may carry it; ReplaceSource rejects a separate output root. `FileSourceAccess.ValidateDestinationAsync` can accept missing parents only beneath that explicit existing root, rejecting network/redirected/non-directory existing ancestors without creating anything. Ordinary single-file plans retain the existing-parent requirement. Immediately before candidate reservation, `JobCoordinator` calls the narrow `ISourceAccess.PrepareDestinationAsync` port for a root-authorized real job, then revalidates collisions/capacity. Infrastructure creates missing components individually with repeated path checks; no-change never prepares. Copy publication and warning approval reuse the captured root and existing source/ownership/no-overwrite checks, with zero additional media allocation at publication.

Empty prepared parents may remain after cancellation or failure. Cleanup never recursively removes output trees and retains its existing candidate/journal ownership contract. These normal-operation path checks do not establish an adversarial filesystem sandbox or a universal power-loss guarantee.

## Phase 2B language, literal-title and forced-subtitle boundary

Core's pure `LanguageRuleMatcher` produces an immutable proposal against one inspection and its current retained IDs. Independent audio/subtitle modes default to unchanged, or retain all exact canonical language matches. The shared frozen ISO table supplies comparison aliases; Infrastructure's preservation policy retains its existing stricter suffix/unknown rules. Matching does not invoke tools or change metadata. Targeted ambiguous metadata or no audio matches leaves the whole file unchanged with explicit issues; no subtitle matches may remove subtitles. The supported tag grammar is documented in `SUPPORTED_FORMATS.md`.

Phase 2B2 adds an optional immutable `TrackTitleFilter` to each language rule. It defaults off; when enabled, trimmed non-blank search text must also occur in the inspected `Title` using `OrdinalIgnoreCase`. Null/blank titles never match. The matcher validates every targeted language before accepting a proposal, including title nonmatches; title matching cannot bypass whole-file manual review. This is a literal conjunction, not a general rule engine, title-only mode or metadata rewrite.

Phase 2B3 adds the default-off `LanguageRules.KeepOnlyForcedSubtitles` value to the captured immutable configuration. Only the subtitle KeepMatching category consumes it, ANDing inspected `MediaTrack.IsForced` with language/optional title after language validation. Unchanged categories ignore the setting. The existing identification adapter supplies Matroska's omitted-flag default (`false`) and rejects malformed booleans; Core does not duplicate that interpretation. No Application lifecycle or Infrastructure production change is needed. The compiled subtitle control shares the category/workspace gate and clears only transient proposals on edits. EN/RU preserves configuration/proposals; New batch retains configuration but clears proposals. No event-level subtitle analysis or player behavior guarantee is introduced.

`BatchCoordinator.PreviewLanguageRules` captures the session revision and every item/inspection/current selection without editing the session. All rows remain visible, including excluded, completed, failed or uninspected rows. Application keeps the issued immutable preview identity and rejects stale or substituted application under the existing operation gate and session lock. Applying reliable changed rows is one atomic selection edit: only affected approvals are cleared, aggregate Review is invalidated, and unrelated rows/results remain exact. A no-op preserves approval/review identities. Per-file editing uses `SetSelection`; aggregate editing uses its revision-bound atomic equivalent; zero-audio consent remains a per-file Desktop decision and is cleared on actual choice changes.

`BatchLanguageRulesViewModel` owns transient rule editing and per-file preview presentation; it does not own jobs. Compiled bindings and aligned EN/RU resources expose explicit Preview/Apply commands and independent optional title controls. Any language/title configuration edit clears the displayed proposal without editing the session; a new preview supersedes the previous issued identity. Relevant batch edits or New batch clear the proposal, delayed notifications re-read the live session, and language/row switches preserve configuration and a valid proposal. New inputs are never automatically matched or approved. Busy/warning/unsafe ownership and conflicting shell operations use the existing unified-workspace availability gates.

## Phase 2C1 portable rule presets

`LanguageRuleConfiguration` shares active-rule validation with the matcher without fabricating inspections. Its content comparison includes ordered raw language values, literal title text, modes and forced-only; deserialized immutable-array identities are irrelevant. Inactive values are retained, with no alias or title normalization for storage.

Application's `RulePresetService` exposes Save as new, Load by stable ID, Rename and Delete through the narrow `IRulePresetStore` port. The pure catalog policy validates names, complete configurations and uniqueness. Presets have no workflow/path/settings fields. Desktop's separate `RulePresetsViewModel` owns selection, localized confirmation and awaitable commands, sharing the existing workspace gate. Selection alone never loads. A load completion must still match selection, editor-configuration and session revisions; changed loads clear only Preview, identical loads preserve it. Catalog operations never approve, apply or run media. Normal close awaits a pending persistence command.

`PortableRulePresetStore` reads `data/rule-presets.json`, schema version **1**, using System.Text.Json and the existing regular-file opener. Missing means an empty catalog. Malformed UTF-8/JSON, missing/null/unknown/duplicate fields, invalid modes, duplicate IDs/names, unsupported versions and exceeded bounds are explicit errors; no entries are silently discarded and the original bytes remain. Escaped property names have a narrow decoding boundary: unpaired UTF-16 surrogates become `InvalidCatalog` through `JsonException`, without a broad exception catch in storage, Application or UI. Manual rule editing stays available, but unsafe catalogs cannot be written until a successful reread.

Bounds are **65,536 actual UTF-8 bytes**, JSON depth **16**, **100** presets, names **80** UTF-16 code units, **32** language values per category, **64** code units per language value and **1,024** per title. The first reached bound applies; 100 maximally sized presets need not fit. Names trim surrounding spaces, reject control characters and compare with `OrdinalIgnoreCase`; renaming an entry's own case is allowed. User names, language values/order and title text remain display data, never paths or translated resources.

Each mutation takes a fail-fast exclusive OS lock on the permanent regular sibling `rule-presets.lock`, rereads the latest complete catalog and applies an ID-based intent, preserving another cooperating instance's unrelated entries. Windows uses an exclusive verified file handle; Linux x64 uses no-follow/nonblocking open, regular-inode verification and exclusive nonblocking `flock`. Contention returns Busy; neither operation waits indefinitely or deletes the stable lock file. These are cooperating-instance protections, not a defense against an actor replacing arbitrary parent directories.

The complete proposal is validated and its actual serialized size checked before a uniquely owned sibling temporary file is created. The file is flushed before same-directory replacement. Precommit failure preserves the previous catalog; cleanup can remove only that operation's still-owned temporary file, and a secondary failure cannot mask the primary one. Successful replacement consumes the temporary path, which is no longer eligible for deletion. Committed outcomes remain distinct from cleanup issues at the Application boundary. This is normal-operation atomic replacement, not a promise of power-loss durability or an automatic corruption-repair system.

Startup restores the catalog without selecting or loading a preset. New batch retains the catalog, selected preset and current rule values while clearing proposals; no automatic application follows later inspection. UI-language changes affect only resources. Delete confirmation rechecks the current workspace write gate both for command availability and at execution, while keeping its captured stable identity; declining remains available when writes become blocked. Preset overwrite/update, import/export and built-ins remain outside this slice. Queue-list restoration uses its separate listing boundary below.

## Process boundary

Production executables are absolute app-relative paths. `ProcessStartInfo.ArgumentList` and `UseShellExecute=false` keep paths out of shell parsing. Both streams drain asynchronously even when retained diagnostics reach their bound; excessive/truncated structured data is a failure. Probe/startup operations have bounds; a valid large remux is not subject to a tiny fixed deadline.

Cancellation terminates and awaits the owned process, including verification operations. A failed termination is reported and prohibits deletion of a candidate that may still be written. Target-specific descendant termination and window-shutdown behavior require runtime acceptance; helper tests alone do not establish every OS behavior.

## Persistence and recovery

Application-owned settings, bounded local diagnostics, and versioned ownership records live in `data` beside the executable. English is the first-launch/default language; persisted languages are `en`/`ru`. JSON protocol values and plan semantics are culture invariant. An unwritable portable data location must be visible and prevent media writes that cannot be journaled safely. Required data/ownership availability is separate from `LanguagePreferenceFailed`: a preference-only read/save failure produces a localized session-only notice without changing healthy media authority. Only a current successful language operation clears that preference cause; it cannot clear an ownership/data failure. Ownership discovery still runs after a preference error.

Ownership records describe only temporary output and publication stages. Bounded JSON reads first use the shared regular-file handle check, so a FIFO named as a record, marker or settings file cannot block startup before size validation. Deserialized nullable records are untrusted: version, stage, process ID/start ticks, nonempty operation ID, complete hexadecimal token, canonical local paths, exact adjacent layout/record filename and matching marker are validated before dereferencing or using their evidence. Malformed JSON and missing/null/invalid fields produce visible `InvalidRecord` entries with the raw record path and manual-review guidance. They never authorize cleanup, deletion or process termination; original record/marker/candidate files are retained. Settings failure does not prevent an independent ownership scan.

On restart the application offers cleanup after validating ownership and only when the original owner is gone and no candidate exists. A recovered media candidate remains unresolved because parent death does not prove the former worker stopped writing; it is never automatically deleted. A new operation may start safely from the source. Old verification is never trusted for publication; stale PIDs are never killed; a matching final filename does not prove publication. The saved unfinished listing can be restored explicitly with fresh authority as described below. There is no automatic retry, byte resume, or deletion by glob.

## Unfinished queue-list recovery

Application `QueueList` contains ordered source paths, intended optional destinations, inclusion and immutable folder origin/output-root intent. `BatchSession.CaptureQueueList` excludes completed/no-change and every result with a published path, even after a later failure. `SetDestination` records intent and invalidates changed approval/Review while preserving uninspected source failures. `BatchCoordinator.RestoreQueueList` shares the existing operation gate, requires an empty safe session and atomically issues new uninspected item IDs at a new revision. Inspections, backend-local selections, zero-audio consent, approvals, Review and jobs are absent. Missing/changed files and collisions are rechecked through the normal fresh inspection/planning pipeline.

Infrastructure `PortableQueueListStore` uses `data/queue-list.json`, schema **2** (legacy schema 1 reads as Copy), **65,536 actual UTF-8 bytes**, depth **16**, **100** entries and **4,096 UTF-16 code units per path field**. Required/unknown/duplicate fields, invalid Unicode, versions, revision IDs and inconsistent relative provenance reject the complete record. Missing files are an empty list with no revision; explicit empty records retain a revision. Sources need not exist during storage: the later filesystem/media checks remain authoritative.

Every write takes the permanent regular `queue-list.lock` using the existing OS exclusion implementation (Windows exclusive handle; Linux no-follow/nonblocking regular open and `flock`), rereads the record and compares the caller's expected revision. Contention is Busy; stale writers are Conflict. Linux disposal explicitly unlocks before closing and is idempotent: an inherited/duplicated descriptor must not retain a completed operation's lock. This follows the open-file-description semantics of [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html); a deterministic real-`dup` regression covers both immediate reacquisition and repeated disposal without unlocking a later owner. Preset storage shares this corrected primitive. The complete validated UTF-8 payload is flushed into a unique sibling temporary file before same-filesystem replacement. Failure before replacement preserves the old record; cleanup checks the owned temporary file's actual identity before deletion. Primary, committed and secondary-cleanup outcomes stay distinct. This does not promise power-loss durability or adversarial parent-directory isolation.

Desktop `QueueRecoveryViewModel` presents an explicit startup Restore/Discard choice without populating the batch. It serializes/coalesces metadata checkpoints on current session changes, awaits the initial checkpoint before Run and pending writes on normal shutdown, and rejects stale startup reads by revision. New batch's empty checkpoint follows any older in-flight write. Equal listing content does not rewrite the record. The global recovery notice remains visible independently of the selected file or subordinate panel. Queue errors preserve manual operation and remain separate from media-ownership failures; no invalid record is silently overwritten. Reload is explicit and requires an empty current list. Rule configuration, presets, appearance and interface language remain separate stores.

Discard publishes a revision-checked empty listing; it never deletes sources, outputs, ownership records or candidates. Existing ownership recovery remains conservative and independent. A crash between publication and its next listing checkpoint may leave a stale source entry. For Copy, fresh validation detects the already existing destination and refuses overwrite. Restoring ReplaceSource recovers intent only; another replacement requires fresh inspection, track selection and explicit Review of the current source. No launch automatically inspects, approves, retries or dispatches anything.

## Verification level

Per-job structural and semantic metadata checks are separate from integration payload checks. The adapter compares the output to the approved retained mapping, deliberately accounts for permitted identifier/container-layout changes, checks XML chapters/tags where supported, and checks attachment metadata. One explicit ISO alias table serves track/chapter/tag comparison without culture-dependent rewriting. A narrow AAC-LC policy can recognize a newly inferred 1024-sample DefaultDuration from unchanged codec configuration; known durations, codec properties and independent timestamp/count checks remain strict.

Integration fixtures compare retained VP8/PCM/SRT and direct FFmpeg-origin H264/AAC/SRT payloads, attachment contents and original source hashes. The real batch case permutes one source's track order/IDs and independently retains different content from each input, comparing every retained payload and both original hashes. Controlled synchronization tests cover queue overlap, late changes, warning/failure/cleanup pauses and cancellation boundaries. Real cancellation evidence retains the observed worker process handle, proves it is active at cancellation and then awaits its exit; buffered progress from an exited worker is insufficient. Controlled ports/process helpers, headless UI and native desktop acceptance remain separate forms of evidence. See `SUPPORTED_FORMATS.md` for the concrete limits and `PLAN.md` for executed results.

## Portable application updates

`Application.Updates` defines stable release identities, numeric version comparison and narrow update/preferences ports. `GitHubUpdateService` checks the public MovieSift stable release asynchronously after startup. A disabled preference, offline GitHub or malformed response does not prevent media use. Only an exact newer platform archive with a SHA256 digest can be offered. Startup performs a check; download/install require an explicit action. Desktop shows one dismissible notification and keeps an update action in the existing settings panel and header.

Staging verifies the download size/hash, bounded archive paths, complete packaged SHA256 manifest, runtime and assembly version. Linux internal file aliases are materialized as regular files; external links and special entries are rejected. The current bundled helper and its shared runtime are copied into private adjacent storage and checked before launch. No downloaded script or arbitrary release asset is executed as an installer.

The shell reserves media editing while installation is requested, waits for preference saves and refuses handoff during active work, warnings, interrupted ownership or unresolved cleanup. A shared application lease prevents the external helper from installing while another cooperating instance is alive; the helper waits for the exact parent process lifetime before acquiring its exclusive lease. It preserves `data` and unknown user files, moves the old complete application to a backup and switches in the prepared tree. The two directory moves are not described as one atomic filesystem operation. A failed switch rolls back where ownership is established, otherwise the previous tree and a recovery report remain.

The restarted desktop acknowledges completion of initialization. A known failed start restores the old tree; a still-running unacknowledged process is not killed or overwritten. The previous tree remains available in the update session's `previous` directory for manual recovery. Users can remove that backup after checking the new version. Power loss between directory moves may require manual restoration. Public 1.0.0 has no updater; the first updater-enabled release must be installed manually. Published archives are never silently replaced with a different implementation.
